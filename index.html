On unikernels, MirageOS & the limits of optimization

"We can only see a short distance ahead, but we can see plenty there that needs to be done."
— Alan Turing

Unikernels are a clean idea: compile type-safe OCaml into a single-purpose image, drop the unused POSIX user-space, and boot in microseconds. I still like that discipline. It taught me to ask what a process is actually for before wrapping it in another runtime.

In production, isolation is only half the work. Networks partition, nodes disappear, and writes disagree. Spending weeks shaving kilobytes off a binary while leaving service boundaries brittle is just optimization theater.

What I keep from that unikernel work is module parameterization: domain logic stays independent of I/O drivers. The rest is ordinary hygiene — bounded retries, explicit compensations, and designing for partial failure from the start. In pahukama.com's Ariadne kernel, that split is the part that has held up.

pahukama.com & Ariadne framework

Modular monolith & distributed saga engine

OCaml · Ariadne framework · domain-driven design

Context. Built for pahukama.com on top of our custom Ariadne framework to handle multi-step e-commerce orders. An external workflow orchestrator would have been the default; we did not need one yet.

Design. Domain boundaries stay modular inside an OCaml functor-parameterized kernel. An asynchronous in-memory bus coordinates multi-step transactions paired with explicit backward compensations, so retries stay idempotent across flaky network calls without a distributed lock service.

(* Ariadne core: Functor-parameterized saga step *)
module Make_Saga (Tx : TRANSACTION_STORE) (Bus : IN_MEMORY_BUS) = struct
  val execute : order_intent -> (unit, domain_error) result Lwt.t
  val compensate : order_id -> reason -> unit Lwt.t
end

Outcome. Live in production serving customers with zero external orchestration runtimes or background daemon maintenance. Multi-step transactions and failure boundaries hold at compile time, eliminating the retreads that usually eat a small team's roadmap once real traffic arrives.

Trade-off. OCaml and strict functor boundaries take more upfront thought than reaching for a looser dynamic stack, and every compensation is still a code path we must design and verify ourselves. We pay that cost once up front to gain stable abstractions we do not have to keep rewriting, and no external workflow engine to debug at 3 a.m.

Embedded analytics, real-time observability & zero-copy lakehouse

DuckDB · AWS S3 Parquet · Real-time Telemetry · Frugal Architecture

Context. It is easy to split the data stack into two idle bills: a metrics SaaS for live operations and a warehouse for historical reporting, both running whether anyone is looking.

Design. Ariadne keeps both jobs in one footprint. An in-memory telemetry ring covers live health and anomaly detection; structured events flush asynchronously to Parquet on S3. Historical aggregations run as in-process SQL through an embedded DuckDB worker.

-- Zero-copy S3 Parquet query execution via embedded runtime
SELECT date_trunc('day', event_time) AS bucket, count(1) AS tx_count
FROM read_parquet('s3://pahukama-telemetry/events/*/*.parquet')
GROUP BY 1 ORDER BY 1 DESC LIMIT 30; -- p50: ~140ms

Outcome. Immediate, live operational observability paired with sub-second CRM analytical querying across historical datasets at near-zero recurring idle spend, sidestepping third-party monitoring subscriptions and cluster leases.

Trade-off. Analytical aggregations and live telemetry share the host's memory envelope. We bound ring buffer capacities, queue analytical queries deterministically, and accept occasional S3 cold-fetch variance in exchange for deleting redundant data infrastructure.

Resilient projections & reactive state idempotency

HTMX · Asynchronous FRP principles · server-side rendering

Context. Some surfaces do not need a client-side state machine. We wanted to avoid hydrating a second copy of the world in the browser just to submit a form.

Design. For those flows, Ariadne serves HTML fragments and lets HTMX swap them in place, with token-backed deduplication so retries do not double-submit. Interactions are just requests; the server remains the source of truth.

Outcome. A single source of truth on the server, zero hydration bugs, and mutations rendered idempotent right at the edge without callback cascades.

Trade-off. User interactions pay a server round-trip. We accept that latency on these flows in exchange for deleting a client-side synchronization layer. Other product surfaces still need a real frontend — that is the TypeScript work below.

Modular analytics shell in TypeScript (Vue & React)

TypeScript · Vue · React · Domain-tailored analytics

Context. Analytics reporting, streaming metric dashboards, and interactive ledger exploration place fundamentally different demands on the client. Forcing every visualization problem into a single front-end toolchain creates poor compromises across reactivity, charting ecosystems, and rendering performance.

Design. A typed microfrontend shell coordinates analytics modules as isolated domain islands. Vue handles fast, lightweight operational metrics and form-heavy filter panels, while React powers complex chart exploration and state-heavy graph canvases. The host shell provides session, theme tokens, and streaming telemetry channels over typed contracts, freeing each analytics domain to pick the best renderer for its problem.

// Shell contract: modular analytics islands bound by domain data channels
type IslandHost<TParams = Record<string, unknown>> = {
  mount: (el: HTMLElement, ctx: AnalyticsCtx<TParams>) => () => void
}
type AnalyticsWorkspace = Record<DomainViewId, IslandHost>

Outcome. Analytics surfaces match their specific computational and rendering requirements rather than being forced into a lowest-common-denominator stack. Engineers can optimize or refactor an individual reporting view without risking operational dashboards.

Trade-off. Multiple view libraries in the bundle require strict shell code-splitting and asset loading discipline. Contract changes between the shell's data stream and the islands must stay versioned and backward compatible.
